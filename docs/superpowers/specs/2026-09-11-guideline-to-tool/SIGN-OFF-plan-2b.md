### D-2b-2 `lookup_fill` sidecar realised as DERIVED `{table_value, override}` + `audit_log` reason — spec §4 "sidecar {table_value, override, reason}" read as semantics, not storage

- **Built:** `table_value` and `override` are computed at render (`resolveLookupFill`, `isOverridden` in `src/lib/eval/lookup-fill.ts`); nothing but the engineer's scalar is stored in `project_parameters`. `reason` is persisted through the existing `recordManualOverride` → `audit_log` (`action='manual_override'`, `equationNumber = 'lookup:<TABLE_CODE>'`) — the same path engine-output overrides use (`manual-override-pill.tsx`, `overrides.ts`). The `✓ Abweichung begründet` confirmation is keyed by `(fieldId, value)` in a module-scoped map (pre-existing pattern from the pill) and is cleared by "übernehmen" or by any value change.
- **Why:** persisting `table_value` would copy a table cell into `project_parameters` (single-source invariant); `override` is a function of two values already held.
- **Alternative if you want it stored:** `project_parameters.value_json` on the same row — needs a `FieldValue` variant + `saveWorksheet` / `page.tsx` / snapshot changes (one column per `dataType` today); a follow-up plan, not a two-liner.
- **Known consequence (Task 7 deferred minor):** in FILL mode the widget writes the table value on open, so a fresh worksheet with a `lookup_fill` field is "dirty" before the engineer types anything.

### D-2b-7 a11y: read-only controls are `disabled`, not `readOnly` + `aria-readonly` (Task 2 ruling)

- **Built:** in `RegisterEditor` / `ReferenceField` / `LookupFillField` a locked instance disables every input/select/checkbox/button (the brief's pin `readOnly disables add / select / number / text / toggle / remove`).
